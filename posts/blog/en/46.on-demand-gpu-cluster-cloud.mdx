# Best On-Demand GPU Cluster Cloud: How to Choose and Scale with Glows.ai

The best on-demand GPU cluster cloud is the one that completes your distributed workload within its time, quality and budget requirements. Glows.ai offers On-Demand Cloud, Virtualized On-Demand Clusters and Bare Metal Clusters, giving teams several infrastructure paths as a project grows beyond a single GPU.

Start by deciding whether the work needs coordinated GPUs or simply more independent workers. That distinction determines what to ask about networking, orchestration and billing. This guide explains how to choose a configuration, build a useful pilot and evaluate Glows.ai against the job you actually need to finish.

## What counts as a GPU cluster?

A GPU cluster coordinates resources across machines. Some jobs communicate continuously between GPUs; others distribute largely independent tasks. A multi-GPU server is one machine with several accelerators, while a multi-node cluster introduces communication between servers as well.

Renting several instances does not, by itself, establish a coordinated training system. The framework, network, storage and launch process must support the intended execution pattern.

| Workload | What additional GPUs accomplish | First question |
| --- | --- | --- |
| Independent experiments | Run more trials at once | Can each worker run without frequent communication? |
| Data-parallel training | Divide batches and exchange updates | Does communication preserve useful scaling? |
| Model-parallel training | Distribute model computation and state | Does the complete memory and topology plan work? |
| Distributed inference | Spread a model or serving workload | Is the goal memory capacity, throughput or both? |

For independent experiments, a pool of workers may be sufficient. For tightly coupled training, the connections between workers can decide whether the additional GPUs earn their cost.

Use On-Demand Cloud to establish a baseline. Discuss Virtualized On-Demand Clusters when you need a coordinated configuration, and Bare Metal Clusters when the workload or operating requirements call for that deployment model. Obtain configuration-specific details before choosing between them.

## Choose the workload before choosing the cluster

Write a short execution brief: model or application, framework version, training method, precision, input size, batch settings, dataset location and completion target. State whether you need one result sooner or many separate results in parallel.

For training, include the validation threshold. Faster steps are useful only if the resulting model still meets the task requirement. For inference, include request lengths, concurrency, output quality and latency targets.

Memory planning must cover the actual execution method. Weights are only part of training memory; gradients, optimizer state, activations and temporary buffers also contribute. During serving, runtime buffers and the KV cache can become substantial. Adding nominal VRAM figures does not create a single automatically usable memory pool.

## Compare the configuration around the GPUs

Ask for a written configuration covering GPU count and variant, GPUs per node, CPU and RAM, local and shared storage, and the connections within and between nodes.

Then confirm how the job starts. Does the proposed setup support your framework's distributed backend? Who installs or manages the orchestrator? Which network paths and permissions must your application use?

Do not infer InfiniBand, NVLink, RDMA, a managed scheduler or a bandwidth figure from the word “cluster.” On Glows.ai, full 8× H100 nodes support NVLink, while RTX 4090, L40S, and RTX PRO 6000 connect multiple GPUs over PCIe. NCCL is supported for multi-GPU communication, and Mesh Clustering puts instances in the same region on a private network. For multi-node clusters, ask us for the topology and operational responsibilities of the specific proposal.

## Measure scaling with one unchanged task

Run a representative baseline on the smallest viable configuration. Repeat the same workload on the proposed larger allocation, preserving the input, training objective and acceptance conditions.

Record completed work per second, total elapsed time, GPU count, memory use, data-loading time, communication overhead and checkpoint duration. Inspect slow workers: synchronized jobs can spend time waiting for a single bottleneck. The Monitor view on each instance page shows GPU utilization and memory over time, which helps you find the worker holding the others back.

For the same amount of completed work:

Speedup = baseline runtime ÷ larger-configuration runtime.

If the baseline uses one GPU, scaling efficiency = speedup ÷ larger GPU count. For a multi-GPU baseline, use the ratio of GPU counts instead. These calculations describe measured scaling, not a promised platform result.

## Calculate GPU-hours before interpreting the hourly rate

The following example is hypothetical. It assumes the same completed task and the same per-GPU rate, and excludes separate service charges.

| Example allocation | Completion time | GPU-hours |
| --- | --- | --- |
| One GPU | 8 hours | 8 |
| Four GPUs | 3 hours | 12 |
| Four GPUs, a different measured outcome | 1.5 hours | 6 |

The three-hour outcome finishes sooner but consumes 50% more GPU-hours. The 1.5-hour outcome consumes 25% fewer. Neither follows automatically from renting four cards.

For the invoice, apply the actual quote and its billing rules. If a quote is per node, use the node price; do not multiply it again as though it were a per-GPU price. Glows.ai on-demand instances are billed per second with no minimum rental time, and data transfer is not normally charged separately. Virtualized On-Demand Clusters and Bare Metal Clusters are quoted per configuration, so confirm minimum allocation, commitment, and setup time in the quote.

## Make failure and handoff part of the pilot

Save a checkpoint or intermediate result, then test whether the job can resume using the intended storage arrangement. For training, resumption may require optimizer and scheduler state as well as weights. On Glows.ai, every instance in the same region can mount the same Datadrive, so all workers can read one dataset and write checkpoints to one place that remains after the instances are released.

Keep a run record with the image identifier, code commit, model and dataset revisions, launch command, worker count and artifact locations. Ask another authorized teammate to reproduce the launch procedure. Shared access is useful; explicit instructions make that access operational.

Agree how to release the allocation after the run. On-demand instances stop billing when they are released, and the Glows.ai SDK API lets you release them from your workflow once the job finishes, so idle nodes don't keep billing.

## Questions before choosing a cluster

### Is a cluster always better than a single GPU?

No. A larger allocation can improve completion time or experiment throughput, but coordination and data movement add work. Use a cluster when the complete task benefits from it.

### Does Glows.ai offer on-demand and bare-metal cluster options?

Yes. Virtualized On-Demand Clusters let you scale up or down without reserving a long-term cluster, while Bare Metal Clusters give you dedicated hardware with full control for long-term training. Contact [hi@glows.ai](mailto:hi@glows.ai) with your workload to get the size, topology, and terms for your job.

### Can I price a cluster using a public H100 instance rate?

For a single 8-GPU node, yes: an on-demand 8× H100 instance is listed at $20.72 per hour, exactly eight times the single-H100 rate. For multi-node clusters, use a configuration-specific quote, since node composition, networking, and purchasing terms affect the price.

### What should the first Glows.ai pilot establish?

Memory fit, useful scaling, recovery, team handoff and the complete charge for an accepted result. Those findings provide a sound basis for expanding capacity.
