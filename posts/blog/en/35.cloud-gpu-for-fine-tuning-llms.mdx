# Choosing the Right Cloud GPU for Fine-Tuning LLMs: A Developer’s Guide

When choosing the best cloud GPU for fine-tuning LLMs, compare memory fit, software compatibility, and the cost of a completed training run. An NVIDIA RTX 4090 with 24 GB of VRAM can be a practical starting point for smaller LoRA or QLoRA experiments. Larger models, longer contexts, or full-parameter training may require more memory or multiple GPUs. Validate the configuration with a short pilot before committing to a longer run.

## 1. Match the GPU to your fine-tuning method

The memory needed to load a model is only part of the training requirement. Leave room for gradients, optimizer states, activations, and temporary buffers. Model size, precision, sequence length, micro-batch size, and the training method all affect peak memory use.

- Full fine-tuning: Updates all model parameters. Depending on the model and optimizer, the training state can require substantially more memory than the weights alone.

- LoRA: Trains a smaller set of adapter parameters while keeping the base model frozen. This reduces trainable state, but base-model weights and activations still occupy memory.

- QLoRA: Combines a quantized base model with trainable adapters to reduce memory requirements. The model, quantization libraries, and training framework must be compatible.

| Configuration | When to evaluate it | What to verify |
| --- | --- | --- |
| RTX 4090 · 24 GB VRAM | Smaller LoRA or QLoRA pilots | Peak memory at your intended sequence length and micro-batch size |
| A100 80GB or H100 80GB | Jobs needing more memory than a 24 GB GPU provides | Memory headroom, runtime, and cost at the same target quality |
| Multiple GPUs | Jobs that exceed a single GPU’s memory or need more throughput | Framework support, interconnect, and actual scaling efficiency |

Multiple GPUs do not automatically provide one shared pool of VRAM. Techniques such as FSDP, ZeRO, tensor parallelism, or pipeline parallelism need suitable software and hardware support. Confirm the available GPU configuration and node topology before planning a distributed run.

## 3. Optimize cost per completed run

The lowest hourly price does not necessarily produce the lowest training bill. A faster GPU may finish the same task sooner, while a smaller GPU may need a slower configuration to stay within memory limits.

GPU compute cost = GPU count × hourly rate per GPU × billable runtime in hours

For illustration, a single RTX 4090 running for 10 hours at $0.49 per GPU-hour costs $4.90 in GPU compute. If the same workload reaches the same target validation quality on one A100 80GB in four hours, compute costs $4.80 at $1.20 per GPU-hour. These runtimes are hypothetical, not benchmark results.

Include any applicable storage, data-transfer, and other service charges when calculating the full project cost. Account for setup time, idle instances, and failed-run retries as well.

Measure memory and throughput after changing training settings. Gradient checkpointing trades extra computation for lower activation memory; it does not necessarily shorten a run. Saving recovery checkpoints is a separate operation that adds storage I/O but can reduce lost work after a failure.

## 4. Build a repeatable training workflow

A suitable environment matters as much as the GPU. The Glows.ai image catalog includes PyTorch environments and LLaMA-Factory. Check the selected image’s configuration and compatibility before starting; an available image does not guarantee that every model or training recipe will run unchanged.

1. Select the environment. Match the model and fine-tuning framework to the image’s Python, CUDA, PyTorch, and quantization-library versions. Choose a training environment rather than assuming an inference image is suitable for fine-tuning.

2. Prepare access and data. Use SSH or JupyterLab to configure the job. Check dataset permissions, tokenization, train/validation splits, and model-license requirements before uploading data or downloading weights.

3. Record the configuration. Version the code, dataset, base model, tokenizer, dependency list, and hyperparameters. Record random seeds and relevant runtime settings to make experiments easier to repeat and compare.

4. Plan checkpoint storage. Choose a storage location that will remain available after the training instance ends. Confirm retention, access, and recovery behavior, then test saving and reloading a checkpoint before a long run.

5. Coordinate team access. For shared work, Glows.ai Team brings GPU resources, environments, datasets, permissions, and quotas into one workspace. Agree on naming, ownership, and budget limits before running parallel experiments.

## 6. Validate the configuration before scaling

Run a representative pilot using the intended model, sequence length, and training method. A short run can expose memory and compatibility problems; it is not a substitute for evaluating the final model.

- Memory: Record peak VRAM use, including validation and checkpoint-saving stages, and leave room for workload variation.

- Throughput: Measure useful training throughput and check whether data loading or checkpoint I/O is limiting the GPU.

- Quality: Track a validation metric that reflects the task. Compare configurations at the same target quality, not merely the same elapsed time.

- Recovery: Test checkpoint save and reload. If you need to resume training, preserve the relevant optimizer, scheduler, and other training state as well as model weights.

- Cost: Estimate the complete run from measured performance and reassess after a longer trial. Include evaluation, retries, and idle compute.

### Check data-handling requirements separately

GPU performance does not establish security or regulatory suitability. Before using sensitive data, confirm processing location, access controls, encryption in transit and at rest, log handling, retention and deletion policies, and any required contractual protections. Do not assume a globally distributed service provides a particular data-residency guarantee.

### Plan the handoff to inference

Export the trained weights or adapters together with the base-model and tokenizer versions and configuration. Check that the serving runtime supports the architecture, quantization, and adapter format; merge adapters only if the deployment workflow requires and supports it. Validate output quality and load behavior before directing production traffic to the model.

Glows.ai offers Inference on Cloud for autoscaling inference and Inference on Dedicated Cloud for isolated inference resources. Confirm model compatibility and deployment requirements separately from the training setup.

### Is a lower hourly GPU price always cheaper?

No. Compare GPU count, billable runtime, and other applicable charges for the same task and target quality. A higher-rate GPU can cost less overall if it completes the job sufficiently faster. Use measured training performance rather than assuming a fixed speedup.

Version the code, data, base model, tokenizer, dependencies, and training settings. Save checkpoints to storage with confirmed retention beyond the instance lifecycle, and test restoration. A saved environment alone does not capture every dependency or guarantee identical results.

### When should I consider multiple GPUs?

Consider multiple GPUs when a suitable single GPU cannot fit the training job or when measured scaling improves completion time or cost. Confirm that the framework, interconnect, and node topology support your parallelism strategy. More GPUs do not guarantee a proportional speedup.
